# Regression proof

Use for a reproducible bug with a practical automated or runtime check. Do not require a new test for cosmetic changes or invent a test that only mirrors the implementation.

1. Identify the exact trigger, expected behavior and failing observation from the user's report or accepted requirements. Choose a check that fails for that reason. Run it before changing production code where practical, then rerun the same assertion after the fix. Record the command or browser actions, runtime/environment, revisions and relevant output.
2. If the fix already exists, or the claim is that a bug existed on a particular base, verify on that explicitly identified revision. Do not assume every bug reproduces on master: a PR can introduce its own bug. For a temporary isolated baseline, follow the host-owned checkout rules in the shared contract and the user’s explicit agreement; do not silently create shell worktrees that bypass Codex setup. Use native support where available; create an extra user-owned task only on explicit request, and preserve the original checkout and all unrelated changes. Otherwise use an available matching checkout or existing trustworthy before-fix evidence. If neither is available, mark before-fix proof unverified rather than requiring a new worktree or disturbing the current checkout. Port only the minimal test/fixture needed, and record any adaptation. Never stash/reset/switch the user's working tree for this check.
3. Inspect the actual assertion or runtime symptom. A nonzero exit, missing import, compilation failure, absent fixture, unauthenticated page or disconnected API is not proof of the bug. Report such a run as blocked or inconclusive and diagnose the environment separately. A pre-fix pass can mean the reproduction is insufficient or the bug is already fixed; investigate before asserting success.
4. Rerun the same check after the fix and require the intended expectation to pass. For a user-visible bug, verify the original trigger on the same interface when available; a unit test is not a substitute for an untested integration claim. Verify relevant adjacent cases without broadening into unrelated cleanup.
5. If a failing-before/passing-after test is impractical, state why and use the closest observable before/after runtime evidence. If that is also unavailable, label regression proof unverified and say what is needed; do not weaken the test, inflate timeouts or fabricate a failure. Continue independent checks.
6. Preserve evidence before cleanup. Leave native worktrees to the host’s lifecycle or an explicitly requested native cleanup action; do not remove them with shell Git commands. Remove only other temporary resources created for this check and authorized for cleanup. Inspect their status before cleanup; if unexpected work appeared, stop cleanup and report it. Never use forced removal to hide a restoration or ownership problem. Tests and the fix may share one coherent commit; proving a failure does not require publishing a broken commit.
