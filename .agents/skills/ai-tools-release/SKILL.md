# Release AI Tools

Run from this repository root (three directories above this skill). GitHub CI publishes the public Git marketplace and release ZIPs. This maintainer workflow prepares those downloads and supports a separately requested account upload; it does not add a fourth product or replace the Git installer. For an ordinary installation update, follow [updates](../../../docs/updates.md).

1. Run `pnpm update:prepare` (or `--tag release-SHA` for a requested release). Read the returned plan. It downloads immutable release ZIPs, requires successful main-push CI, verifies checksums and release fingerprints, validates packages, and starts each MCP server with disposable data. For a preparation-only request, report the plan, comparisons and pending compatibility checks, then stop. Preparation does **not** publish or establish saved-state compatibility.
2. For account publication, resolve exact current listing IDs using live account metadata and any separately maintained private mapping. Retain existing identities, including Workbench's. Never commit workspace IDs to this public repository. Supply an existing private mapping to preparation with `--workspace-ids /absolute/path/to/private/listing-ids.json`; the default plan has no listing IDs. For unmapped products, search the intended workspace for an existing listing before creating one; a local installed plugin is not a shared listing. Confirm owner, scope, audience, current version and edit eligibility. Do not infer an ID from the name. Do not use a personal account to replace a workspace listing.
3. Retrieve the current published files using source tools (`get_plugin_files` / `get_owned_plugin_archive`) when available, otherwise the listing's **Download plugin ZIP** in the Work browser profile. Keep current release IDs and extract sources into a private temporary directory with one subfolder per product. Use `scripts/extract-release.py ARCHIVE DESTINATION` for ZIPs. Rerun `pnpm update:prepare --tag TAG --published DIRECTORY`. Missing current sources remain unverified; do not treat them as new listings without checking discovery. Unchanged packages need no upload. Compare effective root/legacy manifests, MCP settings, skills, assets and every removed file. Preserve current default prompts, integrations, presentation, scope and audience; resolve unexpected losses before publishing. A full upload may overlay files, so omitted obsolete files need supported explicit deletion. Stop if deletion semantics or eligibility cannot be established.
4. Follow [compatibility](../../../docs/compatibility.md) before replacing builds. Compare current saved-state readers with the candidate, document any migration, and verify the exact candidate on disposable saved-state copies. Use existing behavior fixtures and `scripts/check-saved-state.mjs` as supporting evidence, not proof of a different downloaded build. Never point a candidate at live data for a smoke check. Sauron's first portable installation may need an explicit database migration; do not migrate data or edit schedules just to publish. Record compatibility evidence and unresolved native tests in a private `verification.json` next to the plan. Do not upload until compatibility is established for the affected update.
5. Show the product/version changes and any effect on users. A request to publish/upload this account release authorizes that publication; requests to prepare, explain or refresh a Git installation do not. Invoke an available supported `update_plugin` with the exact ID, verified archive, observed `expected_release_id`, and required `delete_paths`. Otherwise use the existing listing's **Upload new version** browser control. If the listing changed meanwhile, reread and reconcile before retrying. When a product has no shared listing, create it in the intended workspace using the verified ZIP; keep its default audience unchanged unless the user authorized sharing. Do not duplicate Workbench or fall back to an admin GitHub sync flow. If tools/account access cannot complete a step, leave it pending and report the precise blocker.
6. After uploading, read back the current version/release, inventory and relevant files, and verify the package content matches (allow only documented host-generated compatibility files). Verify removed files are absent and ID/audience remain unchanged. Save a private `publication.json` next to the plan with per-product ID, URL, prior/new release IDs, version and readback evidence. If delivery is uncertain, inspect the listing before retrying. Never record successful publication on an attempted upload alone. Save newly verified listing IDs only in the separate private mapping, preserving existing bindings.

Report plugin links and versions, pending items, and native desktop activation separately from account publication. Reopen panels to check activated versions when the host is accessible; package smoke tests cannot prove native Workbench chat launch/resume or teammate installation. Do not reset user data or modify installed caches.
